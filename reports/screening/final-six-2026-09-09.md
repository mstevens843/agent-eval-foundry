## Execution record

Eleven fresh attempts were authorized (two per package for four packages, three for
snapshot recovery, which had never run its opposite-provider slots); only **six were
actually needed**, because four packages stopped early once reaching 5/6 became
impossible. The campaign initially launched with three concurrent slots — one each for
incremental-build-repair, variant-cache-repair and issued-report-repair (Trial 6 each) —
confirmed running via `docker ps`. **Mid-campaign, the user explicitly raised concurrency
from three to six.** Because the original three-slot scheduler's own concurrency limit
was fixed at process start, a separate expansion controller was used instead of editing
it: it paused the original scheduler with `SIGSTOP` (confirmed via `ps -o stat`, not
merely assumed), adopted its three in-flight attempts by polling for their own completion
records without signaling or otherwise touching those live Docker containers or
credential brokers, and launched three additional slots (incremental-build-repair Trial 7,
temporal-capacity-repair Trial 6, snapshot-recovery-repair Trial 5). All six ran under the
same signed, subscription-only JobStore reservations, 2 CPUs/2 GiB per container, and
10,800-second budgets as every prior trial. No attempt came close to the timeout; the
fastest (temporal-capacity-repair) ran 7m19s, the longest (incremental-build-repair Trial 7)
28m37s. All six reached a clean `completed` state with no invalid execution or
infrastructure error, and zero errors were recorded across the whole batch. After every
attempt was scored, the superseded original scheduler — confirmed still paused, never
resumed — was terminated with `SIGKILL`; an earlier `SIGTERM` remained pending while
the process was stopped. No live container or credential broker was signaled at any point. All
5,438 manifest-listed files (151,948,284 bytes) across the six completed records were
reverified with zero errors.

### Failure and pass mechanisms

- **Incremental build (21) — six failures across both providers.** Trials 6 and 7
  were fresh Claude attempts, following Claude Trial 5 and Codex Trials 2–4. Both new
  checkers build a final artifact ledger and validate published handles against that
  completed ledger without checking whether the compiler had issued each handle when
  it was published. The `premature-publication` control exposes that omission. Code
  inspection confirms the same gap described in the earlier attempts. Independent
  rehashing now confirms that **all six** checker-grade-summary files, Trials 2–7,
  match `689fe9f88a21705d4a226324a31cbd35b1570c39bd9396148e8d39d5fc50daa9`.
  Their submitted checker source hashes are all distinct. Matching grades corroborate
  the observed recurrence; the code and failing control explain it.
- **Variant cache (19) and issued report (25) — passed their next attempt, retiring the
  package.** Both packages' fresh Codex checkers (Trial 6) caught the specific candidates
  the earlier Claude attempts had missed (`wildcard-eviction` in cache Trials 2–4;
  `reverse-dependency-order` in issued-report Trial 4), matching what their own Trial 5 Codex
  checkers had already done. With 3 failures and only 1 remaining slot each, the maximum
  reachable total dropped to 3+1=4 — below 5/6 — so Trial 7 was never dispatched for
  either package. Each ends its six-run set at 3 failures out of 5 scored attempts (3
  Claude + 2 Codex), one attempt short of the full three-per-provider balance, because the
  outcome was already settled.
- **Temporal capacity (10) — the coverage correction is what reopened it, and its pass
  closed it again.** Before this campaign, temporal capacity's own Trial 5 section had
  already concluded a ceiling of 2+2=4 using the *raw* recorded numbers. The final-six
  audit's correction — flipping Trial 3's recorded pass to an effective fail because its
  checker accepted a genuine zero-query no-work execution the real harness rejects —
  raised the effective failure count to 3, making the ceiling 3+2=5 and reopening the
  package for one more attempt. Trial 6's checker correctly rejected the new coverage
  fixture's negative case (`"record pages were not exhausted"`) and passed the base
  service/checker suite cleanly, bringing the package to 3 failures out of 5 scored
  attempts — unable to reach 5/6 in this fixed six-attempt set, so Trial 7 was never dispatched.
  The original grades and the separate historical corrections remain linked in the evidence.
- **Snapshot recovery (11) — first-ever Claude attempt, coverage correction, still below
  threshold.** The audit similarly flipped snapshot recovery's Trial 3 recorded pass to
  an effective fail (its checker wrongly rejected a valid atomic-transaction pattern —
  write a temporary value, replace it, commit — as an "out-of-scope write"). This
  package had never run an opposite-provider attempt before this campaign; Trial 5 was
  its first-ever Claude submission, and it passed both the base suite and the new
  coverage fixture cleanly. Effective history is now 2 failures out of 4 scored attempts
  (3 Codex + 1 Claude) — with at most 2 remaining attempts, the ceiling is 2+2=4, below
  5/6, so Trials 6 and 7 (both already authorized) were never dispatched.
