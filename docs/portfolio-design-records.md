# Professional portfolio construction records

Prompt 4, 2026-09-06. These are pre-implementation decisions, not qualification results.
The assignment permits local deterministic construction and controls only. Human
solve times below are estimates; no human solve or model hardness is asserted.

## Shared implementation boundary

Retain PackageRecord, assemblePackage, materializeAssembly, assurance and stage
policy. Reuse the protected operation protocol and UID-separated child lifecycle
from Prompt 3 for multi-file submissions. A new professional package gets its own
contract/version, public workspace and private domain adapter. No generic kernel
or historical trial is reinterpreted. Final artifacts must reproduce independently
of ignored plans and of the source checkout.

Use four new domain-specific multi-file repair applications. Node modules are
loaded only by an unprivileged process; the authority owns inputs, observations,
browser and grading. The public client can request documented operations, not
evaluate arbitrary code in the authority. Memory uses actual writable disk and
fresh processes. Browser operations drive Chromium, not a simulated DOM.

## Browser replay repair — first new production type

Useful outcome: replay recorded multi-step form workflows after remounts, delayed
readiness and deferred confirmation, without wrong-entity or duplicate effects.
Starting assets: existing browser-backed prototype/harness types and scenarios;
retain its real DOM and remount concerns, retire built-in subject dispatch and
page-owned effect counters for this new package. Keep the old spike historical.

Build a recorder, trace normalization, selector resolver, form executor and replay
journal. Public UI has ordinary entity/form fields and a documented deterministic
render queue. Evidence is available through live DOM reads, pending transitions,
confirmation and backend receipts. Normalized trace values, current target,
completion of every step/attempt and collateral preservation are all material.
Effects come from real event handlers to a protected backend binding.

Expert strategy (120–180 minutes estimated): distinguish a recorded locator from
current identity; drain render transitions and re-resolve; populate current form
values; observe/accept any actual confirmation; reconcile receipts per trace step.
Alternative: eager preflight and backend-receipt reconciliation rather than a
persistent handle cache. Near-misses: first-candidate resolution, stale reads,
confirmation omission, typed-value loss, replay duplication and earlier-report lies.
Easy route: a generic drain/re-resolve wrapper. Multi-step input/confirmation and
receipt lifecycle require more than that wrapper, but agents may still solve it.

## Native CAA repair

Useful outcome: issue/refuse each multi-name order with correct concurrent authority
association and persistent cache semantics. Existing complete Go service and
protected native route remain the primary asset, not the small CAA kernel.
Retain cached/current boundaries, indeterminate answers, all-or-nothing issuance,
cross-order cache effects and unrelated cache preservation.

Expert strategy (90–150 minutes estimated): keyed concurrent responses, complete
per-name decisions, deliberate error handling and selective cache writeback.
Alternative keyed collectors already exist. Assess narrow interaction coverage
before adding any new requirement. Reject width-only additions and artificial
UNKNOWN receipt semantics. The remaining easy route may be a short keyed planner;
if no further legitimate independent obligation improves it, keep the strong valid
artifact and report that uncertainty instead of inventing a hidden rule.

## Persistent knowledge revision repair

Useful outcome: ingest versioned source facts and derived records, survive actual
serialization/restart, resolve current revisions and execute authorized exports
with complete lineage and correct values. Modules: ingestion, storage, derivation,
policy, consumer and audit. Source revisions can update/retract inputs; historical
provenance cannot be inferred just from a matching string. Legitimate trusted
updates and untrusted text are data, not instructions to the authoring agent.

Expert strategy (120–180 minutes estimated): persist immutable versioned source
records, resolve derivations with cycle/missing/retracted handling, propagate
authority through every dependency, and bind exports/audits to actual versions.
Alternative: append-only revision journal versus atomic snapshot map. There is no
unreachable UNKNOWN state. Near-misses: dropped lineage on disk, stale memoization,
one-parent attribution, overwritten history, value-only trust and blanket refusal.
Easy route: a complete DAG evaluator. Integrating revisions, persistence, current
grants and exact lineage remains the substantive repair, not more injection strings.

## Delegated budget workflow repair

Useful outcome: complete eligible queued spends for several owners/delegates under
shared limits and current grants, reconcile repeated deliveries and uncertain
responses, leave unrelated balances untouched. Modules: queue, identity, budget,
authority client, receipt reconciliation and durable journal.

Expert strategy (120–180 minutes estimated): group by owner/wallet/grant, allocate
budget in declared request order, use action-scoped stable identities, refresh
changed grants, reconcile accepted-but-unacknowledged spends through receipts.
Alternative: reserve planned prefix then reconcile versus receipt-first sequential
allocation. Domain is a fictional integer-credit service, not financial advice.
Near-misses: per-request rather than aggregate budget, delegate as owner, stale
grant version, retry double-debit, lost accepted action and unrelated cleanup.
Easy route: serializing every spend. Serial execution is legal; it still must handle
receipts, revisions and cumulative identities correctly. Do not ban it to add hardness.

## Deployment compatibility rollout repair

Useful outcome: converge a scoped fleet to compatible healthy releases and exact
alias/cache bindings, or restore each failed target's own previous state; preserve
unrequested resources. Modules: inventory, compatibility planning, deployment,
telemetry selection, binding/cache publication and cleanup/recovery journal.

Expert strategy (120–180 minutes estimated): stage per-consumer compatible versions,
observe telemetry for actual deployment generation, publish matching bindings only
after healthy evidence, restore failed scopes and clean only newly unused artifacts.
Alternative: per-target staged transactions versus two-pass deploy/observe/publish.
Near-misses: stale telemetry, correct-count wrong-binding, global rollback, dangling
cache, early alias publication and skipped target. This is not a renamed durable-key
kernel: compatibility joins and multi-resource rollback shape the solution.
Easy route: conservative two-phase rollout; legal, and still integrates generation,
compatibility, heterogeneous old state and collateral-preservation obligations.

## Evidence interpretation and transfer origin

Protected observations, positive work, narrow controls, accepted alternatives and
frozen artifacts are specific engineering transfers from the outbox process.
Interacting obligations and incomplete self-checks are conceptual hypotheses only.
All domain-specific authority, persistence, browser and compatibility rules need
their own local proof. The six historical outbox zeros remain disputed/unresolved;
old memory host failures and unpinned live-DOM effort are not new hardness evidence.

Selection and validation controls must be labelled by actual consultation history.
After a control has guided construction, call it development/regression, not held
out. Later fresh controls can validate a frozen selection once; record any repair
that consumes them. No release/hardness stage is granted by these design records.
