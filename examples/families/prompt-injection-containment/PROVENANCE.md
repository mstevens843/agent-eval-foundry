# Prompt-injection containment — provenance and limitations

The second family measured end to end, and the first the foundry produced rather than inherited.
Everything in `matrix.json` is generated by running code in this repository; nothing is transcribed.

## How to reproduce

```bash
pnpm build
node dist/cli.js family scenarios   # the declared space and the measured selection
node dist/cli.js family run         # reference + 9 mutants -> matrix.json
node dist/cli.js family report      # the family report
node dist/cli.js family axis        # the axis report
node dist/cli.js cross-family       # comparison against durable-approval-outbox
```

| | |
|---|---|
| declared parameter space | 432 points |
| measured scenarios | 128 |
| subjects | 1 reference + 9 mutants |
| matrix cells | 1,152, all measured |
| reference failures | 0 |
| independent axes | 4 |
| null-model mean | 16.7 (ceiling 124) |

## What a cell means

A cell records which named checks a subject failed on a scenario. `{"failed": []}` is a pass. There
are no `null` cells: every subject runs on every scenario in-process, so the not-measured case that
dominates the SWE-bench corpus does not arise here.

Ground truth is the **harness tool ledger** plus the **scenario definition**, never the subject's own
report. The `exactly_allowed` and `no_forbidden_call` checks read the ledger; `decisions_match_ledger`
exists specifically to catch a subject whose account of itself disagrees with what it actually did.

## The limitation that matters most

**The bank is nine mutants written alongside the verifier, not independently submitted
implementations.** This is the opposite provenance from the SWE-bench corpus, and it cuts the other
way:

- The SWE-bench axis count (215 over 500 instances) is a discovery about how real systems fail.
- This axis count (4 over 128 scenarios) is a **lower bound on the verifier's discriminating power,
  by construction.** The mutants were written to be caught. That they are caught is a check on the
  verifier, not a finding about difficulty.

**No agent has attempted this family.** Its difficulty is therefore unevidenced, and the ship report
records it as HOLD rather than SHIP for exactly that reason — a `difficulty-evidenced` gate was added
to the gate table after this family exposed the gap.

## Other limitations

- **In-process isolation.** The ledger is a frozen facade passed to the subject, not a socket in
  another process at another privilege level. The source project needed real process separation
  because its subjects were arbitrary agent-written code; here they are modules in this repository. A
  hostile subject could reach past its arguments. This is a measured mini-benchmark, not a hardened
  task.
- **The policy is unusually explicit** — eight numbered rules in a published evaluation order. That
  is deliberate for fairness and it lowers the difficulty ceiling: a careful implementation can
  satisfy it mechanically. Whether a capable agent finds it hard is untested, and "already-solved" is
  the most likely way this family dies.
- **Scenario realism is stylised.** Segments are short synthetic strings, not real emails or
  documents. The family tests provenance tracking, not natural-language robustness, and an
  implementation that passes here has not been shown to survive a real injection corpus.
- **Attack coverage is five shapes.** Authority grab, scope expansion, secret egress, approval
  confusion and tool-output chaining. Real injection taxonomies are larger.
- **`nop-faker` is dead weight in the bank** — it is caught by every discriminating scenario, so it
  separates no pair of them. It is retained because it guards the trivial regression, not because it
  contributes to the axis count.

## A defect this family found in itself

The first version of the generator scored `secret-exfiltrator` and `approval-confuser` at **0 of 144**
— neither mutant was ever caught. Both scenarios were being blocked, so they looked correct, but they
blocked at `P2_CAPABILITY_NOT_GRANTED` because no grant existed for the `mail` and `acl` capabilities.
They never reached `P5` or `P6`, the rules they were built to test.

Two changes followed: grants were added so those scenarios reach their governing rule, and
`mechanism_fired` now asserts that an attack scenario is blocked **by its governing rule** rather than
merely blocked. A scenario that stops testing its mechanism now fails instead of passing quietly.

This is the same error the source project documented as *validating that a trap is robust is not the
same as identifying which parameter controls it* — and it is the reason the mutant bank exists.
